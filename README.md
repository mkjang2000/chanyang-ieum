# 찬양이음

찬양이음은 교회 찬양팀이 일반 예배와 수련회·성경학교 같은 행사의 콘티와 악보를 함께 관리하는 자체 호스팅 웹앱입니다. 모바일·태블릿 뷰어, 역할별 권한, 실시간 메모와 진행 알림을 지원합니다.

## 주요 기능

- 일반 예배와 행사 콘티를 한 달력에서 통합 조회
- 교회별 예배 프리셋, 기본 시간, 시작 악기 설정
- 이미지 직접 업로드, 저장 악보 재사용, 카카오 이미지 검색
- PDF 악보 페이지 자동 분리 및 제목 OCR
- 저장 악보 원본 관리와 중복 제거
- 모바일·태블릿 대응 연속 스크롤 악보 뷰어
- 핀치 줌, 화면 자동 맞춤, 전체 화면
- 곡별 Key, 교회 편성에 맞춘 시작 악기, 곡 전환, 메모 관리
- 반주자의 곡별 Key·악보 변경 신청, 두 악보 비교 승인·반려 및 이력 조회
- 메모 편집자 표시 및 실시간 갱신
- 관리자 설정형 실시간 진행 알림과 개인 퀵버튼
- 원본 이미지와 전체 콘티 PDF 다운로드
- 만료 및 폐기가 가능한 외부 공유 링크
- 로그인 기록, 강제 로그아웃, 사용자 및 시스템 관리

## 권한

| 역할 | 권한 |
| --- | --- |
| 관리자 | 전체 기능, 사용자·예배·진행 알림·시스템 관리 |
| 인도자 | 본인이 담당하는 콘티 등록·수정·삭제, 변경 요청 승인·반려 및 진행 알림 전송 |
| 반주자 | 콘티 조회, 악보별 메모 추가·수정, Key·악보 변경 신청 및 본인 요청 이력 조회 |
| 성도 | 조회 전용 |

관리자가 다른 인도자를 담당자로 지정해 콘티를 등록하면 해당 인도자도 그 콘티를 관리할 수 있습니다.

### 악보 변경 요청

콘티 뷰어 상단의 **변경 요청** 버튼에서 이용합니다.

- 반주자: **변경신청 / 이력확인**. 곡을 선택하고 Key와 악보를 지정합니다. 악보는 이미지 업로드·검색·저장된 악보에서 선택하며 PDF는 지원하지 않습니다. 이력에서 승인 대기 중인 본인 요청을 취소할 수 있습니다.
- 담당 인도자·관리자: **승인대기 / 이력확인**. 요청 당시 악보와 요청 악보를 좌우·상하로 배치하고 각각 확대·이동하며 비교한 뒤 승인하거나 반려합니다. 반려 사유는 선택입니다.
- 승인 시 해당 콘티의 해당 곡에만 Key와 이미지를 반영합니다. 요청 당시 이미지와 Key, 요청자·처리자 이름, 사유와 처리 시각은 이력에 보관합니다. 콘티를 삭제하면 해당 콘티의 요청 이력도 삭제됩니다.
- 대기 중 원본 악보·Key·곡 제목이 바뀌거나 곡이 삭제된 요청은 승인할 수 없습니다. 반려·취소한 뒤 최신 곡에서 다시 신청합니다.
- 기존 설치본을 업데이트할 때는 앱 실행 전에 `npm run db:migrate`로 요청 이력 테이블을 추가해야 합니다.

## 기술 구성

- Node.js 20 이상
- React 19 + vinext/Vite
- MariaDB
- 서버 파일 시스템 이미지 저장소
- Server-Sent Events(SSE) 기반 실시간 동기화
- Poppler/Tesseract 기반 PDF 변환 및 제목 OCR
- 선택 사항: Audiveris 기반 악보 Key 인식

현재 실시간 채널은 애플리케이션 프로세스 메모리를 사용합니다. 기본 구성처럼 웹 프로세스 하나로 실행해야 하며, 여러 인스턴스로 확장하려면 Redis Pub/Sub 같은 외부 메시지 계층이 필요합니다.

## Docker로 바로 실행

Docker Engine과 Docker Compose 플러그인만 설치되어 있으면 MariaDB를 별도로 준비하지 않아도 됩니다.

```bash
git clone https://github.com/mkjang2000/chanyang-ieum.git
cd chanyang-ieum
cp docker.env.example .env
```

`.env`의 `DB_PASSWORD`를 충분히 긴 임의 문자열로 바꾸고, 이미지 검색을 사용할 경우 `KAKAO_REST_API_KEY`도 입력합니다. 그다음 아래 명령으로 앱과 DB를 함께 시작합니다.

```bash
docker compose up -d --build
docker compose ps
```

기본 주소는 `http://127.0.0.1:3011`입니다. 첫 접속 시 만드는 계정이 관리자가 됩니다. 다른 기기에서 컨테이너 포트로 직접 접속하려면 `.env`의 `APP_BIND`를 `0.0.0.0`으로 바꾸세요. 공개 운영에서는 기본값인 `127.0.0.1`을 유지하고 nginx나 Caddy 같은 HTTPS 리버스 프록시를 앞에 두는 방식을 권장합니다.

```bash
docker compose logs -f app       # 애플리케이션 로그
docker compose restart app       # 애플리케이션 재시작
docker compose down              # 컨테이너 중지 (데이터 유지)
docker compose down --volumes    # DB와 악보까지 완전 삭제하므로 주의
```

Compose 구성은 다음을 자동으로 처리합니다.

- MariaDB가 준비될 때까지 대기한 뒤 DB 스키마 생성·업데이트
- PDF 분리용 Poppler와 한글·영문 제목 OCR용 Tesseract 제공
- DB를 `database-data`, 악보 원본을 `image-data` 볼륨에 영구 저장
- 앱과 DB 헬스체크 및 장애 시 자동 재시작

Audiveris 기반 Key 자동 인식은 이미지 용량과 Java 의존성이 커서 기본 Docker 이미지에는 포함하지 않습니다. 나머지 콘티·PDF·OCR 기능은 기본 이미지에서 바로 사용할 수 있습니다.

## 설치 요구 사항

필수:

- Node.js 20 이상과 npm
- MariaDB 10.6 이상
- PDF 가져오기를 위한 Poppler 명령어: `pdfinfo`, `pdftoppm`, `pdftotext`
- 한글 제목 OCR을 위한 Tesseract와 `kor`, `eng` 언어 데이터

선택:

- 인터넷 악보 이미지 검색: 카카오 디벨로퍼스 REST API 키

Ubuntu/Debian 계열의 PDF/OCR 필수 패키지 예시는 다음과 같습니다.

```bash
sudo apt install poppler-utils tesseract-ocr tesseract-ocr-kor tesseract-ocr-eng
```

## 빠른 시작

```bash
git clone https://github.com/mkjang2000/chanyang-ieum.git
cd chanyang-ieum
npm ci
cp .env.example .env.local
```

MariaDB에 데이터베이스와 전용 사용자를 만든 뒤 `.env.local`을 수정합니다. 데이터베이스 계정에는 해당 데이터베이스의 테이블 생성·변경·조회·수정 권한이 필요합니다.

```bash

npm run dev
```

개발 서버는 모든 인터페이스에서 열립니다. 외부에 직접 노출하지 말고 방화벽 또는 개발 환경의 포트 전달 기능을 사용하세요.

첫 접속 시 생성하는 첫 번째 계정이 관리자가 됩니다.

### 로그인 동시 처리 제한

비밀번호 검증(scrypt)은 1건당 메모리 64MB 를 쓰기 때문에, 로그인 요청이 한꺼번에 몰리면
계산이 끝나기 전에 서버 메모리가 먼저 바닥납니다. 이를 막기 위해 동시에 검증하는 건수를
`LOGIN_CONCURRENCY`(기본값 `2`)로 제한합니다.

이 제한은 IP 를 보지 않습니다. 교회 와이파이 하나에 찬양단 전원이 접속해도 서버에서는 같은
IP 로 보이므로, IP 기준으로 세면 여러 사람이 각자 한 번씩 실수했을 때 전원이 막히는 문제가
생깁니다. 대신 "지금 계산 중인 건수"만 세기 때문에 차단되는 사용자가 없고, 동시에 몰린
사용자는 순서를 기다렸다가 그대로 처리됩니다. 기본값 `2`에서도 20명이 동시에 로그인하면
마지막 사람까지 1초 안에 끝납니다.

CPU 코어와 메모리에 여유가 있으면 값을 올려도 됩니다. 코어 수 이하를 권장하며, 검증 1건당
64MB 를 잡는다는 점을 고려해 정하세요. 대기 줄이 `LOGIN_QUEUE_LIMIT`(기본값 `50`)까지 차면
그 이후 요청은 기다리지 않고 `429` 로 응답합니다. 정상 사용자 수십 명으로는 닿지 않는
값이라 실질적으로는 대량 자동화 요청만 걸립니다.

현재 처리 현황은 관리자 화면의 시스템 상태에서 확인할 수 있습니다. 카운터는 프로세스
메모리에 있으므로 실시간 채널과 마찬가지로 웹 프로세스 하나로 운영하는 것을 전제합니다.

동시 실행 제한과 별도로 5분 동안 서버 전체 300회, 같은 아이디 20회를 넘는 로그인 요청은
`429`로 거절합니다. 무작위 아이디를 바꾸어 가며 로그인 기록과 DB 부하를 쌓는 요청도 전체
상한에서 차단됩니다. 로그인 기록은 기본 10만 행을 목표 상한으로 두고 오래된 행부터 정리합니다.

프로덕션 서버는 경로별 요청 본문 상한을 `Content-Length` 유무와 관계없이 적용합니다. HTTPS
프록시는 `Host`와 `X-Forwarded-Proto`를 덮어써야 하며, 브라우저의 상태 변경 요청은
`Origin`과 Fetch Metadata가 현재 호스트와 일치해야 합니다. 응답에는 CSP, 클릭재킹 방지,
권한 정책, MIME 스니핑 방지 헤더가 자동으로 추가됩니다.

Docker Compose에서는 `docker.env.example`을 `.env`로 복사해 `APP_BIND`, `APP_PORT`, DB 계정과 선택 기능 키를 설정합니다. 컨테이너 내부의 `HOST`, `PORT`, `DB_HOST`, `IMAGE_STORAGE_DIR`은 `compose.yaml`이 안전한 값으로 지정합니다.

DB 연결은 `DB_SOCKET` 또는 `DB_HOST` 중 하나가 필요합니다. 둘 다 설정하면 Unix 소켓을 우선합니다.

실제 키와 비밀번호는 반드시 `.env.local`에만 저장하세요. `.env.local`은 Git에서 제외됩니다.

## 프로덕션 실행

```bash
npm ci
npm run db:migrate
npm run build
npm start
```

`HOST=127.0.0.1`로 설정하고 nginx, Caddy 같은 HTTPS 리버스 프록시 뒤에서 실행하는 방식을 권장합니다. SSE가 즉시 전달되도록 프록시 버퍼링을 비활성화하고 충분한 읽기 제한 시간을 설정하세요.

nginx 위치 설정의 핵심 예시는 다음과 같습니다.

```nginx
location / {
    proxy_pass http://127.0.0.1:3011;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

## 데이터 보관과 백업

- 콘티·행사·곡·설정·이미지 메타데이터: MariaDB
- 업로드 및 검색으로 선택한 이미지 원본: `IMAGE_STORAGE_DIR`
- DB 스키마와 반복 실행 가능한 마이그레이션: `database/schema.sql`

백업할 때는 DB 덤프와 이미지 디렉터리를 같은 시점에 함께 보관해야 합니다. 복구할 때도 두 자료가 모두 필요합니다.

콘티에서 더 이상 참조하지 않는 찬양과 악보 파일은 정리 대상이 됩니다. 자동 정리는 하루 한 번 검사하며 관리자가 시스템 화면에서 수동으로 실행할 수도 있습니다.

## 보안 및 저작권

- 비밀번호는 scrypt로 해시되어 저장됩니다.
- 로그인 세션은 `HttpOnly`, `SameSite=Lax` 쿠키를 사용합니다.
- 공유 링크는 만료 시간을 가지며 관리자 또는 발급자가 폐기할 수 있습니다.
- 인터넷에서 찾은 악보와 업로드한 악보의 이용 권한은 운영 교회가 직접 확인해야 합니다.
- 저장소에는 실제 교회 계정, DB 덤프, `.env.local`, 악보 이미지나 PDF를 커밋하지 마세요.

### 자동 메트로놈

콘티를 열면 제목 아래에 위아래 2px 여백을 둔 10px 막대가 박자 수만큼 나뉘어 표시됩니다. 첫 박은 빨강, 나머지는 초록이며 현재 박자가 밝아집니다. BPM은 악보 설정 부분에 표시됩니다. 시작 버튼 없이 서버 공통 기준 시각에 맞춰 점멸합니다. 곡 인식은 위쪽 악보 이미지의 75%가 화면 위로 지나간 시점에 다음 곡으로 바뀌며, 개인 스크롤을 따라갑니다.

- 콘티 편집 또는 악보의 BPM 표시에서 박자와 BPM(20~300)을 설정합니다. 탭으로 세 번 이상 두드린 뒤 추정 BPM을 적용할 수 있습니다.
- `이어서` 연결된 구간은 첫 곡의 BPM을 상속합니다. 구간 내에서 악보를 넘겨도 점멸 기준은 유지됩니다. 첫 곡의 BPM이 미정이면 해당 구간은 점멸하지 않습니다.
- 점멸/탭 한 번은 박자 분모의 음표 한 개입니다. 예: 4/4는 4분음표, 6/8은 8분음표이며, 6/8의 점4분음표 기준 템포를 입력하려면 3배로 환산합니다.
- 설정 저장은 실시간으로 전달되며 재접속 시 최신 설정을 다시 받습니다. 서로 다른 BPM 구간을 보고 있거나 설정 변경이 전달 중일 때는 같은 점멸을 기대할 수 없습니다.
- 60Hz 기준 2프레임(약 33ms)은 실제 기기에서 검증해야 하는 목표이며 보장 수치가 아닙니다. 네트워크 경로 비대칭, 화면 갱신 위상, 브라우저 작업 지연의 영향을 받습니다.
- 접속 시 시각을 6번 측정하고, 왕복 지연이 적은 최대 3개 측정의 시계 차이 중앙값을 사용합니다. 왕복 지연 자체로 점멸을 차단하지 않습니다. 측정값이 흔들리면 새 보정값의 반영 비중을 낮추며, 재측정에 따른 시계 보정은 초당 최대 5ms씩 점진적으로 적용합니다. 5초마다 재측정하고, 유효 측정이 30초 넘게 없거나 화면이 백그라운드로 가면 점멸을 중단합니다. 회색 막대의 상태는 마우스를 올리거나 보조 기술로 확인할 수 있습니다. 복귀 시 다시 동기화합니다.

기존 설치에는 `npm run db:migrate`로 `conti_items.bpm`, `time_signature` 열을 추가해야 합니다. Docker는 시작 시 마이그레이션을 적용합니다. 서버 시각 API(`/api/clock`)는 캐시하지 않아야 하며, 서버가 여러 대인 배포는 서버 간 시계 동기화도 필요합니다.
